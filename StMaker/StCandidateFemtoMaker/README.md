# StCandidateFemtoMaker

Femtoscopic pairing of particle candidates produced by independent **reconstruction parts**.
The Maker does not know how a candidate was reconstructed (KFParticle, track PID, ...); the
analysis macro creates the parts and hands them to it. The configuration of an analysis (mainconf and
the YAML files it names) is the analyst's own and lives in `config/`, which is git-ignored.

```text
analysis macro (anaCandidateFemto.C)
  creates  FemtoEventSelector  (e.g. OfficialEventSelection)
           CandidateSource ... (e.g. KfParticleCandidateSource, TrackPidCandidateSource)
        ↓ hands them to (Maker owns them)
StCandidateFemtoMaker  per event: selection → sources → BDT scores → per channel: shared-track rule → SE pairs → ME pairs → pool
        ↓ THnSparse per channel + QA histograms
common/macro/candidate_femto/  CF, purity correction, QA (outside the Maker)
```

- Interfaces: [`include/CandidateSource.h`](../../include/CandidateSource.h) (`FemtoSourceCandidate`,
  `CandidateSource`, `FemtoEventSelector`). No KFParticle types cross them.
- The Maker library links no KFParticle code. KFParticle is needed only by the parts that use it
  (`libStKfParticleCommon.so`, loaded by the runner). There is no KFParticle-specific build rule for
  femto Makers.
- The generic `StFemtoMaker` (φ–p, Λ–nucleus) is a separate, shared Maker with its own provider path;
  this Maker follows its YAML vocabulary (species / channels, `partA_partB`, `hKstarSE_<channel>`)
  but does not modify it.

## Parts

| Part | Where | Provides |
|---|---|---|
| `KfParticleCandidateSource` | `StMaker/kfparticle/` (needs KFParticle) | one `StPicoKFParticleInterface` pass per event; particle keys `xi_minus_kf`, `xi_plus_kf`, `k0s_kf` after the Stage-B cuts of the kf YAML (`KfCandidateCuts`, K0S Λ veto); reconstruction QA histograms (`hKf*`, `hXiMinus_*` / `hXiPlus_*` one charge each, `hK0short_*`) |
| `OfficialEventSelection` | `StMaker/kfparticle/` (uses `KfEventSelection`) | Run21 3 GeV official selection: bad runs, triggers, vertex cuts, positive multiplicities, per-batch pile-up band and cent9 (`official*` keys of the kf YAML); `hKfEventSelection`, `hKfOfficialEventSelection` |
| `TrackPidCandidateSource` | `StMaker/common/` | identified tracks (mainconf key `trackPid`): charge, pT, \|p\|, DCA, nHitsFit, TPC nσ, optional TOF; mass variable = TOF m² |

Adding a particle:
- KFParticle particle: enable it in the interface / kf YAML and add a key to
  `KfParticleCandidateSource` (`SpeciesKeys`, `DaughterNames`, `VariableNames`, `ProcessEvent`). All
  KFParticle particles of a job are found in the same Finder pass.
- Track particle: add a block to the `trackPid` YAML.
- Another reconstruction method: implement `CandidateSource` and create it in the analysis macro.
Then declare the species and channels in the `candidateFemto` YAML. The Maker needs no change.

## Configuration (all from the mainconf)

| mainconf key | Read by | Content |
|---|---|---|
| `candidateFemto` | Maker, analysis macros | species, channels, axes, QA keys, purity-fit and CF keys of the macros ([`CandidateFemtoConfig.h`](CandidateFemtoConfig.h) documents every key) |
| `candidateBdt` (optional) | Maker | per species: the model file and the score-axis edges, plus `outsideTrainingScore` ([`CandidateBdtScorer.h`](CandidateBdtScorer.h)); absent = no BDT |
| `trackPid` | `TrackPidCandidateSource` | track particle selections |
| `kf`, `event`, `centrality` | parts, Maker (ConfigManager) | KFParticle cuts, event cuts, centrality (shared config classes) |
| `mixing` | Maker (ConfigManager) | `nVzBins`, `nCentralityBins` (1 or 9), `bufferSize`, `mixBothDirections`; `mixingMode` must be `bufferAll` |
| `candidateFemtoHist` | Maker (HistManager) | QA histograms, generated by `script/generate_hist_anaCandidateFemto.py` |

These YAML files are read with [`include/FlatYamlConfig.h`](../../include/FlatYamlConfig.h): required
keys are checked, unknown keys are errors, and the resolved path of every file is printed. They are
not registered in `ConfigManager` (no change of shared code per new analysis).

## Output

- `hPairSE_<channel>`, `hPairME_<channel>`: `THnSparseF` with axes
  (k*, cent9, mass class A, mass class B, mass A, mass B, BDT score A, BDT score B); mass class
  0 none, 1 signal, 2 left sideband, 3 right sideband. Windows, sidebands, BDT thresholds,
  centrality selections and purity corrections are chosen afterwards from this one object.
  Projections: [`common/macro/candidate_femto/CandidateFemtoProjection.h`](../../common/macro/candidate_femto/CandidateFemtoProjection.h).
- QA histograms (names in the hist YAML): `hKstar{SE,ME}_<channel>` and `hKstar{SE,ME}VsCent_<channel>`
  (signal × signal quick look); per channel and species, the candidates that enter the channel's pairs
  (`hChannelMassVsCent9_<channel>_<s>`, with a BDT `hChannelMassVsCent9VsScore_<channel>_<s>`; QA only: without
  the partner's BDT threshold they are not the pair population, so the CF macros take purities from `hPairSE`) and the candidates the channel's shared-track rule removed
  (`hChannelSharedTrackRemovedMass_<channel>_<s>`),
  SE pairs still sharing a track (`hShareRejectSE_<channel>`), close-pair Δη–Δφ*, daughter split/merge and
  decay-vertex QA, event QA, all-track PID QA, candidate mass / score / acceptance per species.
- `CandidateFemtoConfiguration`: text of the effective configuration, the YAML files and, per BDT, the
  model description with the md5 of both tree-ensemble files.
- With `writeCandidateTrees: true`: `<output>.tree.root` with `candidates_<species>` for the species of
  `candidateTreeSpecies` (`runId eventId cent9 mass px py pz score`, every source variable, then one flag
  `sharedTrackRemoved_<channel>` per channel of the species) for BDT training and for the score check.
  Every usable candidate is written; the flags record each channel's shared-track decision.

## Pairing rules

- k* with the PDG masses of the YAML (`species_<s>_pdgMass`), PRF relative momentum.
- **Shared tracks (always on), per channel.** The rule concerns the two particles whose correlation the
  channel measures. When a candidate of species A and a candidate of species B of the same event share a
  daughter track and at least one of them is in its signal window, both are removed from that channel: its
  SE and ME pairs, its pool and its `hChannel*` histograms (so the purity is computed from exactly the
  candidates of the channel's pairs). Other channels are not affected: each correlation function is
  computed independently (a candidate removed in one channel stays in the others). Sharing between
  candidates of the same species is not considered (identical-species channels are not supported; if
  they ever are, the rule applies inside such a channel). The per-species histograms and the trees keep every usable candidate.
  A candidate that looks good only by borrowing a track of the partner may come from a pathological
  reconstruction; the rule depends on the mass windows only, not on BDT thresholds chosen later. Pairs
  that still share a track (both outside the signal windows) are rejected in SE
  (`hShareRejectSE_<channel>`). Finish prints the removed counts per channel, species and mass class.
- **Mixing.** Only events with at least one A and one B candidate of the channel (after its shared-track
  rule) take part, as SE pairs exist only there: ME is made from the same kind of events. Order per event:
  SE → ME against the pool → store the event (no self-mixing). Per channel and mixing class (Vz bin ×
  cent9) the pool holds the last `bufferSize` such events. ME = current A × pooled B and (with
  `mixBothDirections`) pooled A × current B, every pair (no random subset), so every event enters ME with
  the same per-pair weight as in SE. Mixing pools live inside one job, so more events per job give fuller pools.
  Finish prints `eventsWithBoth` and the ME/SE pair ratio per channel.
- **ME purity differs from SE purity.** The pool condition is "an A and a B candidate", not "a good A and a good B":
  most ME A candidates come from events without a B in its signal window, and their purity can be much lower than in
  SE. The CF macros therefore fit the purities of SE and ME pairs separately. Restricting the pools to events with a
  good A and a good B gives the same CF without correction, but such events are too rare to fill pools within a job
  and leave the ME side bands empty, so it is not the method.

## BDT

Rules: [`docs/ai/AGENT_RULES.md`](../../docs/ai/AGENT_RULES.md) "Candidate BDT"; procedure:
[`docs/ai/skills/candidate-bdt.md`](../../docs/ai/skills/candidate-bdt.md).

- **Model.** A BDT is a model file `<name>.model.yaml` plus two tree-ensemble files `<name>_f{0,1}.trees.txt`
  (one per fold), written by `common/macro/datadriven_bdt` (Python + xgboost, action `model`) from a
  training on the candidate trees. The model file holds the fold scheme, the training event selection and
  preselection, the learner and the provenance; the input expressions are read from the tree-ensemble
  files. The Maker evaluates the trees itself (`CandidateTreeEnsemble.h`, plain C++): score =
  2p − 1 of the xgboost probability p.
- **Folds.** Two folds by run parity: fold f was trained on runs with `runId % 2 == f`; a candidate is
  scored with the other fold. Models with another fold scheme are refused.
- **Domain.** A candidate that fails the model's event selection or preselection gets
  `outsideTrainingScore` (below -1, alone in the first score bin). Finish prints the count per species
  (`outsideTrainingDomain=`).
- **Variables.** Expressions use the candidate-tree branches (`runId eventId cent9 mass px py pz` and the
  source variables), computed once per candidate and used for both the tree and the score. The flags
  `sharedTrackRemoved_<channel>` are not model variables: a model's selections define where the Maker
  scores, and one score serves every channel, so it must not depend on one channel's decision (the Maker
  refuses such a model). The toolkit never uses the flags as inputs (`inputs.use: all` leaves them out). Flagged candidates
  are excluded from the training sample with the toolkit's `data.trainingSelection` (training only; the
  scoring domain is unchanged).
- **Score axes.** `<s>_scoreEdges`: first bin around `outsideTrainingScore`, the others cover [-1, 1].
  Every threshold to be studied must be an edge; thresholds are chosen in the macros.

```
# candidateBdt YAML
speciesKeys: xi_minus
outsideTrainingScore: -2
xi_minus_model: bdt/<anaName>/<name>.model.yaml   # relative to config/
xi_minus_scoreEdges: -3, -1, 0, 0.05, 0.1, 0.2, 1
```

## One PicoDst pass: candidate store

```text
reconstruction stage (farm, once)   writeCandidateStore: true
  PicoDst → event selection → every part → candidate store (TTree candidateEvents: event record + every candidate of
  every species of every part, daughter-track momenta; + PicoDst-only QA histograms) — no pairs, no BDT
pair stage (any number of times)    same macro, the store file(s) as input
  stores → StoredCandidateSource (same part names, species, variables) → the same Maker code → THnSparse, QA, trees
```

- [`CandidateStore.h`](CandidateStore.h): writer, reader, `StoredCandidateSource`. Nothing particle-specific: the layout comes
  from the parts. Stored values are the parts' / PicoDst's `Float_t` and integers, so the pair stage reproduces a one-pass job
  exactly (bin by bin, every histogram, THnSparse and candidate tree).
- `analysis/anaCandidateFemto.C` decides by the input: `.picoDst.root` (or a list of them) → PicoDst chain; any other `.root`
  (or a list of them) → pair stage. Mixed lists stop.
- The pair stage adds the stored reconstruction-stage histograms to its output and stops if a histogram was filled in both
  stages; it also stops if its event-cut YAML differs from the stored one in content (comments and blank lines are ignored;
  mixing classes and vertex radius depend on it).
  The pair stage reads whole stores (`nEvents` must be -1; the macro refuses a limit), since the stored reconstruction-stage
  histograms of every store are added in full. For a short test give fewer store files.
- BDTs are applied only in the pair stage (`candidateBdt` is refused with `writeCandidateStore: true`); species with and without
  a model can be mixed freely (`candidateBdt` `speciesKeys`).

## Running

Mainconfs of one analysis (names as in the `generate_joblist_from_list.py` examples): `main_<anaName>_candidateStore.yaml`
(reconstruction stage, `writeCandidateStore: true`), `main_<anaName>_bdtTraining.yaml` (pair stage with
`writeCandidateTrees: true`, no `candidateBdt`) and `main_<anaName>_bdt.yaml` (pair stage with `candidateBdt`).

```bash
./script/singularity_make.sh <mainconf>
./script/singularity_run_anaCandidateFemto.sh <list> <out.root> <jobid> <nEvents|-1> <mainconf>
# two stages: reconstruction (PicoDst once) and pair stage (stores, no PicoDst)
./script/singularity_run_anaCandidateFemto.sh <picoDst list> <store.root> <jobid> -1 config/mainconf/main_<anaName>_candidateStore.yaml
./script/singularity_run_anaCandidateFemto.sh <store.root or list of stores> <out.root> <jobid> -1 config/mainconf/main_<anaName>_bdt.yaml
# farm: joblists from a file list (a directory of stores gives its non-empty files); then cd job/run && ./submit.sh <joblist>
V=rootfile/<anaName>/<major>
./script/generate_joblist_from_list.py --mainconf config/mainconf/main_<anaName>_candidateStore.yaml \
    --input <picoDst list> --files-per-subjob 3 --label candidateStore --output-dir $V/<store version>/store
./script/generate_joblist_from_list.py --mainconf config/mainconf/main_<anaName>_bdtTraining.yaml \
    --input $V/<store version>/store --files-per-subjob 100 --label bdtTrainingTrees \
    --output-dir $V/<version>/hist --tree-output-dir $V/<version>/tree
./script/generate_joblist_from_list.py --mainconf config/mainconf/main_<anaName>_bdt.yaml \
    --input $V/<store version>/store --files-per-subjob 100 --label bdtAnalysis --output-dir $V/<version>/hist
./script/singularity_purityCorrectedCorrelation.sh <out.root> <mainconf> <channel> <out/prefix> 2 "4,5,6,7,8"
./script/singularity_checkHistCandidateFemto.sh <out.root> <mainconf> <out.pdf> "8;6,7;4,5"
```

## Validation

What the current code is known to satisfy (rerun the relevant check after changing a part, the store or the pairing):

- **Pair stage = one pass.** A reconstruction stage followed by a pair stage gives, bin by bin, the output of a single
  job that does both (every histogram, THnSparse and candidate tree; 5 PicoDst files, 150k events).
- **Pairing rules as written here.** An independent implementation of this README (shared-track rule, pools, mixing,
  k*, BDT scores) reproduces every bin of every pair THnSparse (100 stores, 5M events).
- **BDT scores.** `datadriven_bdt check`: every in-domain Maker score equals the offline score (to 1e-6), every
  candidate outside the domain gets the outside-training score. Without a BDT the output does not depend on the BDT code.
- **Expressions.** `CandidateExpression` equals `TTreeFormula` on every candidate (21 expressions); malformed
  expressions, a model with another fold scheme and score edges without the outside bin are refused.
- **Full statistics.** The two-stage production (a full data set, every file) runs without failed jobs; a rerun of the pair
  stage reproduces the previous merge in every bin.
